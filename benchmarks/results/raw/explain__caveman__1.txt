Race condition: result depends on timing of concurrent access to shared state. Two threads read-modify-write same value, one update lost. Works in tests, fails under load. Hard to reproduce.

Example — lost update:

```python
balance = 100

def withdraw(amount):
    global balance
    if balance >= amount:      # thread A and B both read 100
        balance -= amount      # both write 40, one withdrawal vanishes

# two threads call withdraw(60) at same time
# expected: one succeeds, one fails. actual: both "succeed", balance 40.
```

Fix — make check-and-act atomic with a lock:

```python
import threading
lock = threading.Lock()

def withdraw(amount):
    global balance
    with lock:
        if balance >= amount:
            balance -= amount
            return True
        return False
```

Across processes or machines, a lock in memory is not enough. Use a database transaction with row-level lock (`SELECT ... FOR UPDATE`) or an atomic compare-and-set.

Rule: if code reads a value, decides, then writes it back, and anything else can touch that value in between, you have a race condition.
